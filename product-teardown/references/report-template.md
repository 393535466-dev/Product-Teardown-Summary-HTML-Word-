# 围绕主线的报告结构

这是叙事与深度模板，不是全维度平铺的清单。Word 和 HTML 保留相同主线与结论；最终分别按 document-output.md 和 html-output.md 生成实际文件。

## 主文从一个问题展开

### 1 产品是什么 本次要验证什么

一句话定位、用户、产品类型/主端、原有替代工作流。明确一个主场景、最终交付、成功标准、核心问题及体验范围。首屏给出主要结论与重大限制；不要先铺满覆盖率、编号、权限和长目录。

### 2 跑一个场景 最终交付如何

输入与约束 → 实际走过的路径 → 产物与验收 → 人工干预/修改 → 最重要的发现。展示代表性证据，区分配置可见、过程跑通、结果可用。未完成则说明中断点、为什么影响结论和需要怎样补测。

### 3 沿同一任务分层解释

可按产品实际情况合并小节，主线机制占主要篇幅：
- 市场与商业：为何服务这类用户和任务，最相关竞品/替代方案、收费约束、差异化假设。通常简述，关键时深入。
- 场景与产品机制：总体模块如何围绕主流程协同，关键判断点、正向路径和失败/修改返回；重点展开。
- 技术与协作：总体人/系统/AI 分工、共享对象与更新，再分析决定结果的关键单元，不对所有模块逐一写同等长度卡片。
- 模型与基础：能力来源、模型/服务选择、成本条件、数据和资产复用怎样支撑同一条链；未知实现标假设，不堆无关名词。

每个深拆必须回答“它位于主线哪一步、为什么影响交付、机制是什么、证据与限制是什么”。核心未确认问题在这里可见，不能全部藏在附录。

### 4 整体架构与关键结论

一张图或清晰映射把场景、步骤、分工、关键单元、模型/服务与数据引用连接起来。连接标已知/推断/未知，架构图不是菜单导航图。

回收：它替代了什么工作、真正重要的设计取舍是什么、交付到什么程度、优势和瓶颈有什么依据。优先列少量最高影响的建议/验证动作，说明证据、影响、优先级依据和可观察验证标准。

## 关键单元的 PRD 深拆

嵌入对应流程章节，必要时编号 F01/F02；不单独建立一份与主线脱节的字段目录。

| 内容 | 要回答的问题 |
| --- | --- |
| 位置与职责 | 属于哪个步骤，服务哪项交付约束，为什么重要 |
| 输入与前置条件 | 需要哪些素材/状态/权限，哪些条件已确认 |
| 处理与规则 | 人、系统或 AI 做什么，判断、工具、控制权与移交如何安排 |
| 输出与引用 | 产生什么中间产物，下游谁读取，关联/版本如何保留 |
| 状态与异常 | 处理中/失败/取消/不满意时反馈什么，保留什么，回到哪里 |
| 修改传播 | 上游变更后哪些要更新/重做，哪些确认结果必须保持 |
| 需求与体验取舍 | 机制带来什么好处和成本，是否真的帮助任务完成 |
| 验收与证据 | 可复现的观察、E 来源、确定性、关联 Q；建议验收单列 |

只有影响上述机制的字段、校验、默认值、权限与非功能条件才在正文展开；完整细节可后置。设计推导不能混入既有规则。

## 附录备查

按需要组织，不必全部展示在首屏。HTML 折叠、Word 展开并放到主文之后，不能删除关键细节。

### 其他资料

非核心模块、完整端形态/角色权限、字段清单、次要问题、详细竞品资料等按实际价值保留。未观察不推定没有，未测不能补造。

## 最终检查

只读主文，读者应能复述主场景、从输入到交付的关键步骤、决定结果的机制，以及最大的不确定性。如果只能记住很多功能名、模型名或表格字段，说明主次仍未建立，需要合并与重排。
