# 产品经理视角拆解

回答一个贯穿问题：**这个产品为谁完成什么任务，怎样把输入一步步变成可用交付，哪些设计决定它做得好不好？** 产品经理视角为主，用户体验用于验证流程和交付。默认中文，生成内容一致的 Word（.docx）与 HTML。

## 先定主线与主次

接收链接、名称、截图、录屏或材料；记录日期、版本、端形态、账号与套餐及实际可访问范围。关键信息可推定时先推进，无法确定目标产品或关键任务时集中询问。

先写三项工作约定：
1. **主场景：** 哪类用户在什么触发条件下，把什么输入变成什么交付。默认选最能体现核心价值的一个代表场景，必要时补一个关键变体；用户指定场景优先。
2. **核心问题：** 为理解交付是否成立，需要深入哪几个环节，为什么。通常先选 2—3 个决定性问题；这是聚焦起点，不是强制数量上限。
3. **深度分配：** 主线深拆、支撑简述、附录备查。按 [分层框架与优先级](references/framework.md) 判断；重要性与证据确定性分别记录。

浏览全景用于选主线，不等于每个入口都写一张同等篇幅需求卡。正文的多数分析围绕场景、流程、关键机制和结果；端形态、市场、竞品、收费等解释选择与约束，通常作为支撑。若支付、协作、跨端或权限正是任务成败关键，就提升到主线并说明原因。未验证的核心问题仍在正文突出，不能因为证据不足就让容易观察的按钮顶替它。

## 工作方式

### 1. 产品介绍与初步定位

用简短内容交代目标用户、核心交付、现有替代流程、产品端形态和价值假设。市场与商业只补足为什么有需求、谁付款、何处收费、主要约束与可能壁垒；数据缺失则标未知，不用无关行业背景撑篇幅。定位假设在场景体验后修正。

### 2. 用同一场景检验最终交付

先定义输入、期望产物和可观察成功标准，再走入口 → 输入 → 过程 → 输出 → 实际交付。区分“页面有功能”“过程能完成”和“结果可使用”。先看端到端结果，再回溯是哪一步设计造成结果；用户视角贯穿观察，不另堆一章主观感受。

按任务选择少量评价重点，如交付可用性、约束保持、过程可控、修改恢复、成本时间。无必要不打综合分；需要评分时给出量表、依据、样本和缺失项处理，不能套用参考案例的权重或给未测项打零分。

实测受限时交付范围明确的研究：写清在哪一步中断、已经观察到什么、核心结论还缺什么，不将配置页访问称为完整体验。需要登录、付费、发布、上传或权限变化时遵循当前授权；研究任务本身不是所有外部操作的授权。

### 3. 分层解释同一条任务链

按 [framework.md](references/framework.md) 逐层追问，围绕场景形成因果联系，而不是六份互不相关的清单：

- **市场与商业：** 为什么选这类任务和用户？相对竞品/替代方案的差异、收费与价值如何连接？
- **场景与产品机制（重点）：** 核心模块怎么协同？正向流程有哪些判断点，异常和不满意怎么返回主线？
- **技术与协作：** 每步由人、系统或 AI 做什么，如何移交、确认与更新共享信息？先分析总体协作，再深入决定结果的单元。
- **模型与基础积累（按证据展开）：** 哪些能力依赖模型，哪些来自流程设计、数据和可复用资产？选择、路由、成本与壁垒怎样影响交付？

AI 产品需要时读取 [AI 深拆](references/ai-products.md)；普通产品对应系统服务与业务数据，不强套 Agent。默认选择 2—3 个最相关的竞品/替代方案，围绕同一任务的关键差异比较，不能为矩阵完整扩散到无关功能。仅资料比较时标明，未体验不得排名生成质量。

### 4. 把关键环节还原为 PRD 机制

用一张主流程图标出输入、处理、产物、判断、移交和人工确认，并把失败、修改、取消、返回接到具体节点。对主线中的关键单元按 [需求单元模板](references/report-template.md) 深入：**职责与目的 → 输入和前置条件 → 处理与规则 → 输出与下游引用 → 状态与异常 → 修改后的传播与恢复 → 验收与证据**。

先写业务逻辑及其设计取舍，再补足影响任务的字段、默认值、校验和权限；不是先从所有字段开始。区分对既有行为的还原与用于复现的设计方案。没有证据的接口、数据库、RAG、Agent 数量、系统提示词、模型路由等不写成真实实现。

用主线步骤名称关联需求和证据；复杂时再加 F/E/I/Q 编号，不强制同时建立多套 G/S/M/P/F 标签。辅助模块只概述职责及与主线关系；完整清单与低影响细节放附录。

### 5. 用整体架构回收结论

最后把场景、业务流程、人机分工、关键机制、模型/服务与数据资产汇成整体图或清晰对照，区分已知连接与实现假设。回答它替代原工作流的哪一段、最重要的设计取舍是什么、目前能交付到哪、主要短板和壁垒证据是什么。架构总结不能只重复功能导航。

优先呈现少量会改变任务成败的改进或待验证问题，写清步骤、证据、影响、建议、优先级依据和验证方式；其他问题附录备查。缺频率或成本数据时定性分析，不编造指标、工期和精确收益。

## 证据与可拆解性

来源可用网页、官方帮助、用户材料与实际体验；时效功能/价格/竞品查证日期。网页受限时尝试可用浏览器或连接，仍受限则准确交付已验证部分。

两套判断独立：
- **能拆到哪里：** 可完整拆解本次目标 / 可部分拆解 / 当前无法拆解；写明限制与所需条件。
- **结论确定性：** 确定项有可靠直接依据且限定环境；不确定项写明推理及其他解释；需二次确认项列问题、重要性、方法和所需条件，确认前仍非事实。

证据性质区分直接观察、官方说明、第三方材料、分析推断；官方宣传与实测冲突时并列核实。“没看到”不等于“没有”，模型/角色名称不证明内部实现。核心未确认项在结论和相关节点可见，完整证据放附录；公开交付不包含敏感账号或私人项目内容。

## 交付与检查

默认交付两份可直接打开的实际文件：一份可编辑的 Word 文档（`.docx`）和一份 HTML 报告；Markdown、PDF、HTML 源码或网页截图不能替代 Word 文档。用户明确要求不同格式或只要其中一份时遵循。

先整理一份完整的分析内容与证据清单，再生成两种形式，不分别重写出相互矛盾的结论。读取 [双文件与 Word 输出规范](references/document-output.md) 和 [HTML 输出规范](references/html-output.md)。HTML 可使用 [页面模板](assets/report-template.html) 与 [生成脚本](scripts/render_report.py)，或按内容直接编写；Word 可使用可用的文档工具或 python-docx，具体排版和核对步骤见 document-output.md。

分析结果的表达形式不固定：结论用短段落或重点卡片；竞品、端差异、规则用表格；层级和分支用结构图、流程图；界面分析用截图标注；只有真实且同口径的数据才做数值图表。按解释效果选择，可混合使用，不机械要求每节都有表或图。事实、推断、建议与未确认状态始终在对应内容旁可见。

默认在当前任务可写的 `outputs/product-teardown/<产品与日期>/` 生成同名的 `<产品名>-产品拆解报告.docx` 与 `<产品名>-产品拆解报告.html`，避免覆盖已有报告。优先单文件离线可读：CSS、必要脚本和 SVG 内联，截图可内嵌为 data URL；确需多文件时复制资源到报告旁并完整交付。截图保留来源、时间和说明，图像不得把推断伪装成产品真实界面。HTML 中的流程图必须实际可见，不能只放未渲染的 Mermaid 源码。

页面首屏呈现核心结论、覆盖范围与关键限制，目录可跳转；长需求卡和证据可折叠，影响结论的缺口不能只藏在折叠区。支持窄屏阅读、表格单独横向滚动、图片自适应、打印时展开细节。不重复堆砌摘要、正文、表格和结尾的同一段话。

生成后打开 HTML 检查桌面与窄屏布局、图像和图表、目录、折叠及打印样式，修复遮挡、横向溢出与资源丢失。浏览器不可用时检查结构和资源引用，并说明未完成视觉验证。Word 需检查标题层级、分页、表格、图像、来源和所有展开后的需求细节；HTML 需检查折叠前后的内容。完成两份文件后，按 document-output.md 运行 [双文件结构检查](scripts/check_deliverables.py)，再对照关键结论、范围、版本、编号、表格数值和待确认项的一致性。结构检查不能替代内容判断与视觉检查。仅一份成功时继续补齐另一份；遇到不可解决的工具限制，准确说明未交付的格式，不把半成品称为双文件完成。

最终分别返回 Word 和 HTML 的真实文件链接与少量关键结论，不再粘贴整篇报告。默认本地交付，用户明确要求在线发布时再按其范围部署。

按 report-template.md 组织：产品与主场景 → 场景体验及交付判断 → 围绕主线的分层拆解 → 架构闭环与关键改进；字段大全、非核心模块与完整证据放附录。正文以核心流程和决定结果的环节为重，不将所有维度平铺成同等一级章节。用户明确要求全量清单时另附全景清单，并保留主线。逆向拆解作为 PRD 素材，不声称它是产品团队的原始 PRD；用户明确要求完整 PRD 时，将建议需求与已验证现状分开。

交付前检查：
- 首屏能否说清主场景、最终交付和最关键的产品机制？
- 主线环节是否有充分深度，支撑与附录是否被错误提升为主角？
- 每项深拆能否连接到主流程节点与结果影响，修改后能否回到主线？
- 端、版本、角色和套餐差异是否被误混为统一行为？
- 竞品比较条件是否一致，事实是否有证据，推断是否明确？
- 可拆解性和确定性是否分别记录，关键缺口是否有确认方法？
- 建议和现状是否分开，验收条件能否观察或复现？
- Word 与 HTML 是否都真实生成、内容一致？Word 分页表格是否可读，HTML 图表、窄屏及打印是否可读？

方法来源与取舍见 [案例方法映射](references/case-method.md)。框架吸收场景实测、正逆向流程、逐层追问和整体架构回收，保留本 Skill 的 PRD 主线、证据分级与双文件交付；不把参考案例的模型数量、评分权重或实现推导当作通用事实。
